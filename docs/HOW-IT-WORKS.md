# MAX Sender Server — Как работает проект

> Документ написан простым языком для понимания общей логики без погружения в код.

---

## Что это такое и зачем

MAX Sender Server — это многопользовательский SaaS-сервис для массовой рассылки сообщений в мессенджере MAX. Несколько организаций (учреждений) могут одновременно использовать одну установку на VPS: у каждой свой кабинет, свои аккаунты MAX, свои группы получателей и своя история рассылок. Всё это изолировано друг от друга.

Сервис запускается в Docker на VPS и работает 24/7. Доступ через браузер по HTTPS.

---

## Архитектура — из чего состоит

```
Пользователь (браузер)
      ↓ HTTPS
   Caddy (обратный прокси, TLS)
      ↓
   FastAPI (main.py + app/)   ←→   PostgreSQL (пользователи, подписки)
      ↓                              SQLite per-tenant (профили, группы, кампании)
   Campaign Worker (asyncio)
      ↓
   MAX API (неофициальный)
```

**Технологии:**
- **FastAPI** — веб-сервер, API-эндпоинты
- **PostgreSQL** — SaaS-данные: учреждения, пользователи, подписки, отозванные токены
- **SQLite** — операционные данные каждого тенанта: профили MAX, группы, сообщения, лог отправок, кампании
- **Redis** — rate-limit для защиты от брутфорса (есть fallback на память если Redis упал)
- **Caddy** — HTTPS, автосертификаты Let's Encrypt, обратный прокси
- **asyncio** — воркеры рассылки работают параллельно в одном процессе
- **pymax** — неофициальная библиотека для взаимодействия с MAX API

## Часть 1: Регистрация и вход

### Как появляется новое учреждение

1. Администратор открывает `/auth.html` → форма регистрации
2. Вводит: название организации, email, пароль (дважды)
3. Сервер создаёт в PostgreSQL:
   - запись в таблице `tenants` (учреждение)
   - запись в таблице `users` (пользователь с ролью `user`)
   - всё в одной атомарной транзакции — либо оба создались, либо ничего
4. Затем создаётся папка `data/tenants/{id}/` на диске — там будет храниться SQLite-база этого тенанта, файлы сессий MAX, сообщения
5. Если создание папки провалилось — регистрация откатывается, tenant и user из PG удаляются
6. Пользователь получает JWT-токен и попадает в свой кабинет

### JWT-токен — что внутри и как работает

Токен содержит:
- `sub` — ID пользователя
- `jti` — уникальный ID токена (для отзыва)
- `tenant_id` — к какому учреждению принадлежит
- `role` — `user` или `admin`
- `imp` — флаг "сейчас работаю под чужим аккаунтом" (impersonation)
- `exp` — когда истекает (через 168 часов = 7 дней)

Токен подписан `JWT_SECRET` алгоритмом HS256. Без знания секрета его нельзя подделать.

Пользовательский JWT передаётся только в HttpOnly cookie `max_token` (постоянная при «запомнить меня», иначе сессионная). Заголовок `Authorization: Bearer` принимается только для `INTERNAL_SERVICE_TOKEN` (метрики и внутренний запуск кампании Celery). User JWT в Bearer игнорируется.

### Как работает выход (logout)

При выходе `jti` токена записывается в таблицу `revoked_tokens` в PostgreSQL. Каждый следующий запрос с этим токеном будет отклонён — middleware проверяет отзыв.

## Часть 2: Система безопасности

### Middleware — первый рубеж обороны

На каждый HTTP-запрос работают два слоя middleware (выполняются до того, как запрос попадёт в обработчик):

**Слой 1 — Rate limit авторизации:**
- Считает количество POST-запросов на `/api/auth/login` и `/api/auth/register` с одного IP
- Если больше N запросов за минуту → отвечает 429 (слишком много попыток)
- Данные хранятся в Redis; если Redis недоступен — в памяти (per-процесс)

**Слой 2 — Аутентификация:**
Для каждого запроса:
1. Если путь публичный (`/static`, `/`, `/auth.html`, `/api/health`) → пропускает без проверки
2. Если нет токена → 401
3. Проверяет подпись JWT
4. Проверяет: не отозван ли `jti` в базе
5. Проверяет: существует ли пользователь в PostgreSQL
6. Проверяет: существует ли учреждение (tenant)
7. Устанавливает контекст: кто делает запрос, какой tenant, какая роль
8. Для `POST /api/campaign/start` — проверяет активность подписки

После обработки запроса — контекст сбрасывается (ContextVar — изолирован по корутине).

### Изоляция тенантов

Каждый тенант живёт в своей папке:
```
data/tenants/1/          ← тенант #1
  app.db                 ← его SQLite
  sessions/              ← session.db.enc (Fernet) по profile_id
  messages/active.txt    ← его файл сообщений
  .app_key               ← Fernet-ключ этого data_dir (рядом с sessions)

data/tenants/2/          ← тенант #2 — полностью отдельно
  ...
```

Middleware устанавливает через Python ContextVar (thread-local для asyncio), что текущий запрос принадлежит конкретному тенанту. Все операции с БД идут через `_resolve_data_dir()` / `get_effective_data_dir` — путь конкретного тенанта. Hot path vault/session crypto должен использовать тот же `data_dir` и per-dir кэш (`app.vault` / `vault_store`), а не process-global `_fernet` / `SESSIONS` (ADR 006).

### Роли и права

| Роль | Что может |
|------|-----------|
| `user` | Группы (создать/удалить), аккаунты MAX, Старт/Стоп, сводка. Без паузы, пула сообщений, настроек, прокси, CSV |
| `user` | НЕ может менять глобальные настройки и сообщения (запрещено в middleware) |
| `admin` | Всё + управление всеми учреждениями, подписками, impersonation |
| `service` | Только запуск кампании через `INTERNAL_SERVICE_TOKEN` (используется Celery) |

### Service token (для Celery)

Celery-воркер может запустить кампанию без JWT-токена — он использует `INTERNAL_SERVICE_TOKEN` и передаёт `X-Tenant-Id` заголовок. Middleware видит этот особый токен и даёт доступ только к двум эндпоинтам: `POST /api/campaign/start` и `POST /api/campaign/schedule`.

### Vault — зашифрованные сессии MAX

Сессии MAX-аккаунтов (sqlite-файлы с токенами) на диске хранятся как `session.db.enc` (Fernet). Цель — не оставлять plaintext `session.db` и усложнить случайный доступ к файлам на томе.

Как работает vault (server mode, актуальная модель):
1. В каждом `data_dir` (tenant или local) лежит `.app_key` — сырой Fernet-ключ
2. При первом обращении `ensure_vault_unlocked(data_dir)` создаёт ключ при отсутствии и загружает его в память (per-`data_dir` кэш); PIN/пароль vault в UI не используется
3. Перед работой с MAX — `session.db.enc` расшифровывается во временный `session.db`; после — снова шифруется, plaintext удаляется
4. Старые password-vault файлы (`.app_salt` / `.app_vault`) при обнаружении снимаются; миграция обратно на PIN/Scrypt unlock **не** делается

**Threat model (volume theft):** шифрование — disk-key encryption. Бэкап `max_server_data` содержит и `.app_key`, и ciphertext; кто получил том или такой бэкап, расшифрует сессии. Защита — контроль доступа к volume/бэкапам (см. PRODUCTION-OPS), не отдельный unlock-секрет пользователя. API PIN (Scrypt в `main.py`) — отдельный механизм для HTTP API, не ключ vault.

## Часть 3: Админ-панель

### Что видит администратор

Страница `/admin.html` — отдельная панель только для роли `admin`.

**Список учреждений:** все зарегистрированные организации, их email, дата регистрации, когда истекает подписка.

**Управление подписками:**
- Продлить подписку на N дней от текущего остатка (`max(сейчас, дата окончания) + N`)
- Кнопка «+30 дней» — то же продление на 30 дней
- Отозвать подписку (сразу неактивна)
- Просмотр скоро истекающих подписок (предупреждение за 7 дней и за 1 день)

**Настройки рассылки (админ):**
Вкладка «Настройки рассылки» содержит полный антибан (паузы, окна, роли, presence, дедуп, circuit). Сохранение копируется во все учреждения (ADR 007). Пул воркеров (на карточке пользователя) и секреты (PIN, Telegram) не копируются.

**Impersonation — войти под пользователем:**
Администратор может нажать "Войти в кабинет" у любого учреждения. Сервер ставит сессионную cookie `max_token` с JWT `imp=true` и `tenant_id` этого учреждения, а текущий админский JWT сохраняет в сессионной HttpOnly cookie `max_admin_token`. Выход из impersonation — `POST /api/auth/exit-impersonation` (восстанавливает админскую cookie). `restore-session` отклоняет imp-cookie. Видит ops-инструменты (пауза, пул сообщений, настройки, прокси), которых нет у самого учреждения. Факт входа логируется в `impersonation_log`.

**Удаление учреждения:**
Удаляет тенанта из PostgreSQL и его папку `data/tenants/{id}/` с диска.

**Мониторинг:**
- `/api/health` — состояние PostgreSQL и Redis
- `/metrics` — счётчики в формате Prometheus (сколько отправлено, сколько кампаний, состояние vault и т.д.)

### Жизненный цикл подписки — автоматика

Фоновый цикл (`subscription_lifecycle_loop`) запускается при старте и проверяет каждый час:

1. **За 7 дней до истечения** → отправляет Telegram-уведомление администратору: "Учреждение X, подписка истекает через 7 дней"
2. **За 1 день до истечения** → ещё одно уведомление
3. **Когда подписка истекла** → автоматически останавливает активный воркер рассылки этого тенанта + Telegram-уведомление "Рассылка остановлена"

Уведомления не дублируются: система помнит, что уже отправила на сегодня.

## Часть 4: Личный кабинет пользователя

### Что хранится в SQLite каждого тенанта

```
profiles       — аккаунты MAX (телефоны) с их статусом
groups         — группы MAX для рассылки
group_profiles — привязка: какой аккаунт работает с какой группой
messages       — текущий пул сообщений (загруженный txt)
queue_state    — текущее состояние очереди рассылки (где остановились)
send_log       — лог каждой попытки отправки
campaigns      — история кампаний с итогами
settings       — настройки тенанта (задержки, антибан и т.д.)
antiban_state  — состояние антибана по каждому профилю
```

### Профили (аккаунты MAX)

Каждый профиль — это один номер телефона. Статусы:
- `pending` — добавлен, ещё не авторизован в MAX
- `active` — авторизован, может отправлять
- `needs_reauth` — сессия устарела, нужно переавторизоваться
- `disabled` — вручную отключён или превысил лимит ошибок

### Авторизация в MAX

Когда пользователь нажимает "Войти" у профиля:
1. Открывается подключение через библиотеку `pymax` к MAX API
2. Если настроен прокси для группы — подключение идёт через него (SOCKS5 или HTTP)
3. MAX отправляет SMS с кодом
4. Пользователь вводит код в браузере → он через WebSocket попадает в очередь → pymax его получает
5. Если у аккаунта облачный пароль — запрашивает ещё и его
6. После успешного входа — сессионный файл сохраняется и шифруется vault'ом
7. Следующий раз pymax использует уже сохранённую сессию без SMS

### Группы и прокси

Каждая группа MAX (чат или канал) может иметь свой прокси. Это важно для антибана: разные аккаунты в разных группах выходят с разных IP.

Прокси поддерживаются в форматах:
- `socks5://user:pass@host:port`
- `http://user:pass@host:port`
- Можно задать пул прокси (несколько строк через `;`), тогда разные профили получат разные прокси (ротация по `profile_id % count`)

Перед началом рассылки система проверяет каждый прокси — устанавливает TCP-соединение, проходит SOCKS5/HTTP-хендшейк.

### Сообщения

Пул TXT **общий на сервер**: загружает только администратор (вкладка «Пул сообщений»). Учреждение пул не видит и не меняет. Одна строка — одно сообщение.

Режимы выбора сообщений:
- `random_norepeat` — случайный порядок без повторов до конца пула, потом снова перемешивается
- `round_robin` — последовательно по кругу

В кабинете под сводкой — **журнал** простым языком: «отправлено в «группа» с номера …», «нужен повторный вход», пауза до рабочего окна. Технический живой лог (воркер #N, куски текста) видит только админ при impersonation.

## Часть 5: Как работает рассылка

### Запуск кампании

Когда пользователь нажимает "Запустить":
1. Система проверяет подписку (активна ли)
2. Снапшот всех настроек сохраняется в `campaigns` (какие были параметры в момент старта)
3. `queue_state` устанавливает `running=1`, начальные индексы профиля/группы/сообщения
4. Создаётся asyncio-задача: один воркер (или пул воркеров)

Можно также запустить отложенно (`/api/campaign/schedule`): кампания запустится в указанное время. Scheduler проверяет каждую минуту.

**Пауза vs стоп:** оба останавливают воркер и сбрасывают `auto_run` (планировщик не поднимает рассылку сам). Пауза пишет статус `paused` и **не** сбрасывает индексы очереди. Стоп — статус `stopped`. Продолжить после паузы — снова «Старт». У учреждения в кабинете только Старт/Стоп, без паузы.

### Как работает воркер (основной цикл)

Воркер — это бесконечный async-цикл. На каждой итерации:

```
1. Проверить: мы в окне отправки? → если нет, ждём до открытия окна
2. Сделать случайное "присутствие" (human presence)
3. Взять следующее задание из очереди (claim_next_job)
4. Если очередь исчерпана → завершить кампанию
5. Если нет профилей → завершить с ошибкой
6. Отправить сообщение через MAX API
7. Подождать случайную задержку (антибан)
8. Повторить
```

### Pool воркеров (несколько параллельных)

Настройка `worker_pool_size` (по умолчанию 1) определяет, сколько воркеров работает параллельно.

При `pool_size > 1`:
- Все воркеры одного тенанта берут задания из общей очереди через `claim_next_job` с `CampaignRuntime.claim_lock` — два воркера не возьмут одно задание; тенанты не сериализуют друг друга
- Группа, в которую сейчас пишет другой воркер этого учреждения, пропускается (`groups_in_flight`) — один прокси на группу, без деления на чётные/нечётные
- Воркеры №2, №3... стартуют со случайной задержкой — "расфазировка", чтобы они не отправляли одновременно (это выглядело бы подозрительно)
- Когда очередь заканчивается — первый воркер объявляет `DONE` и завершает кампанию. Остальные видят `STOP` и просто выходят

### Что такое "задание" (job)

Каждое задание содержит:
- `profile` — какой аккаунт MAX отправляет
- `group` — в какую группу MAX
- `text` — текст сообщения
- Индексы для следующего шага (чтобы продолжить с того же места после перезапуска)

## Часть 6: Антибан

Это самая сложная и важная часть. Цель — сделать так, чтобы MAX не заблокировал аккаунты за подозрительную активность.

### A. Временные окна отправки

Настройка `send_windows_weekday` и `send_windows_weekend` задаёт в какие часы работает рассылка.

По умолчанию: `9-13,16-21` в будни и `11-14,17-20` в выходные.

Воркер постоянно проверяет текущее время. Если за пределами окна — ждёт до открытия. Это имитирует то, что обычный человек не пишет сообщения в 3 часа ночи.

Часовой пояс настраивается (`timezone_offset_hours`, по умолчанию UTC+3).

### B. Случайные задержки (не равномерные!)

Между отправками воркер ждёт случайное время. Но не просто `random.uniform(min, max)`.

Используется **логнормальное распределение** (`lognormal_delay_sec`):
- Большинство пауз — в районе середины диапазона
- Редко бывают очень короткие или очень длинные
- Плюс jitter ±40% сверху

Это важно: равномерное распределение легко обнаружить статистически. Логнормальное — похоже на поведение реального человека.

Дополнительно:
- **Утренний jitter 55%** — утром паузы более хаотичные
- **Вечерний jitter 35%** — вечером стабильнее

### C. Дневной лимит на аккаунт

Каждый аккаунт MAX имеет лимит сообщений в день: случайное число между `daily_limit_min` и `daily_limit_max` (по умолчанию 5–10).

Лимит случайно выбирается для каждого аккаунта при старте каждого нового дня — и сохраняется. Это означает, что каждый день разные аккаунты шлют разное количество.

Ежедневно в начале работы система сбрасывает счётчики (`messages_sent_today`) для всех профилей у которых `sent_day` не равен сегодняшнему дню.

### D. Warmup (прогрев новых аккаунтов)

Новые аккаунты нельзя сразу нагружать полным лимитом — это признак бота.

Система `warmup` (включена по умолчанию, 7 дней):
- День 1–2 (возраст аккаунта 0–1 день): лимит 1–2 сообщения
- Далее: плавное линейное увеличение до полного лимита
- После `warmup_days` дней: работает полный лимит

Возраст считается по `created_at` профиля.

### E. Роли на день (skip/active/quiet)

Каждый день утром система перемешивает аккаунты в группе и раздаёт им роли:

- **skip** (~40% аккаунтов) — сегодня не отправляют вообще
- **active** (~30%) — отправляют по полному лимиту
- **quiet** (~30%) — отправляют только 1–2 сообщения

Это имитирует реальное поведение группы людей: не все пишут каждый день, у каждого разная активность.

Параметры настраиваются: `day_skip_percent`, `role_active_percent`, `role_quiet_percent`.

Роли пересчитываются ежедневно — разные каждый день.

### F. Перерывы у аккаунта после N сообщений

После каждых N сообщений (`break_after_n`, по умолчанию 8) аккаунт берёт перерыв на 10–40 минут (`break_min_sec/break_max_sec`).

Это имитирует: "написал несколько сообщений, пошёл по делам".

Перерыв — только у этого конкретного аккаунта. Другие аккаунты в это время продолжают работать.

### G. Случайные короткие и длинные паузы

Помимо основных задержек между сообщениями:

- С вероятностью 8% (`short_pause_chance`) — короткая пауза 30–50 секунд ("задумался")
- С вероятностью 3% (`long_pause_chance`) — длинная пауза 2–5 минут ("отвлёкся")

### H. Lazy days (ленивые дни у старых аккаунтов)

Аккаунты старше `warmup_days` дней иногда работают с пониженным лимитом (`lazy_day_factor = 0.4`). Вероятность 15% (`lazy_day_percent`).

В "ленивый день" аккаунт отправляет не более 40% от обычного лимита.

### I. Circuit breaker

Если у аккаунта подряд `MAX_CONSECUTIVE_ERRORS = 5` ошибок — он "выбивается" на `CIRCUIT_BREAK_MINUTES = 30` минут. В это время воркер его пропускает.

После паузы — circuit закрывается, аккаунт пробует снова.

Если ошибки продолжаются — cooldown нарастает экспоненциально:
- 1 сбой → 2 часа cooldown
- 2 сбоя → 4 часа
- 3 сбоя → 8 часов
- ...до максимум 48 часов

При 8+ сбоях подряд аккаунт переходит в статус `disabled`.

### J. Human presence (присутствие)

Периодически воркер имитирует действия живого пользователя до отправки сообщения:

- С вероятностью 70% — просматривает историю чата (`read_history`)
- С вероятностью 40% — отмечает как прочитанное
- С вероятностью 12% — ставит реакцию (👍 ❤️ 🔥 😂 и другие)
- С вероятностью 5% — просто "сидит онлайн" без действий

### K. Антидубликаты текстов

Система дедупликации (`text_dedupe_enabled`):
- Окно дедупликации = `max(настройка, количество_аккаунтов × 2)` сообщений
- Если текст слишком похож (similarity > `text_similarity_max = 0.72`) на недавно отправленный — пропускается, берётся следующий
- Вариативность длины — иногда берётся укороченная версия сообщения

### L. Retry при ошибке отправки

Если отправка упала с ошибкой:
- Пытается ещё `MAX_RETRY = 3` раза
- Задержки между попытками: 5, 15, 60 секунд
- Если все попытки провалились — записывает в `send_log` status=`failed`, переходит к следующему

### M. Цели кампании

**`daily_limits`** (по умолчанию): кампания работает бесконечно — каждый день аккаунты снова получают лимиты и снова отправляют. Идеально для регулярной рассылки.

**`message_pool`**: кампания заканчивается когда все сообщения из TXT-файла отправлены хотя бы по одному разу.

## Часть 7: Мониторинг и уведомления

### WebSocket статус

Страница кабинета подключается к WebSocket (`/ws/status`). Сервер каждую секунду отправляет:
- Статус воркера (running/stopped/paused)
- Сколько сообщений отправлено/провалилось
- `activity` — человеческий журнал для кабинета
- `log` — технический лог (в UI только у админа)
- Состояние аккаунтов (лимиты, роли, cooldown)

Это позволяет видеть процесс рассылки в реальном времени без обновления страницы.

### Telegram-уведомления

Если настроен `telegram_bot_token` и `telegram_chat_id`:
- Уведомление при завершении кампании (статус, сколько отправлено/ошибок)
- Уведомление при ошибке воркера
- Уведомление об истечении подписки (за 7 дней, за 1 день, при истечении)

Дедупликация: одно и то же уведомление не отправляется чаще раза в `_TG_DEDUPE_SEC`.

### Webhook

Помимо Telegram можно настроить произвольный HTTP-webhook. При завершении кампании туда придёт POST с JSON:
```json
{
  "event": "campaign_finished",
  "status": "completed",
  "reason": "Готово: дневные лимиты исчерпаны",
  "campaign": { "messages_sent": 47, "messages_failed": 0 }
}
```

### Бэкапы

Автоматический бэкап SQLite-базы каждые `backup_interval_hours` часов (по умолчанию 24). Хранится последние `BACKUP_KEEP = 10` копий. Создаётся WAL-checkpoint перед копированием для консистентности.

### Ops Monitor (OpsAlert)

Фоновый цикл проверяет:
- Воркер не завис ли (сравнивает последний `_worker_last_activity` с текущим временем — если > `WORKER_TIMEOUT = 300` сек, считает зависшим)
- Состояние PostgreSQL и Redis
- Настраивает alerting

## Часть 8: Отправка сообщения — детально шаг за шагом

Когда воркер решил отправить сообщение от профиля A в группу B:

1. **Расшифровка сессии**: `session.db.enc` профиля A расшифровывается ключом `.app_key` текущего `data_dir` во временный `session.db`

2. **Создание клиента pymax**: передаётся `phone`, `work_dir` (папка с сессией), прокси (если задан для группы B)

3. **Подключение к MAX API**: через TCP → TLS → MAX протокол. Если сессия действительна — подключается без SMS

4. **Human presence**: перед отправкой делает одно случайное "живое" действие в этом чате

5. **Выбор текста**: из пула берётся следующий текст по выбранному алгоритму (random_norepeat или round_robin), проходит проверку дедупликации

6. **Resolve chat ID**: если у группы ещё нет `max_chat_id` (внутренний ID в MAX) — резолвит его по invite_link. Если нужно — вступает в группу

7. **Отправка**: `client.send_message(chat_id, text)`

8. **Запись в send_log**: `status='sent'`, timestamp

9. **Обновление счётчиков**: `messages_sent_today + 1` для профиля, глобальный counter `messages_sent_total`

10. **Шифрование сессии обратно**: файл снова шифруется

11. **Note human burst**: прибавляется счётчик "отправок подряд", при достижении N — устанавливается перерыв

12. **Закрытие клиента**: безопасное закрытие TCP-соединения (с обработкой SSL close_notify ошибок)

13. **Задержка**: логнормальная пауза перед следующей итерацией

## Часть 9: Планировщик (Celery)

Опционально можно включить Celery (`USE_CELERY=1`) — это позволяет:
- Запускать кампании по расписанию через внешний планировщик
- Горизонтальное масштабирование в будущем

Celery-воркер (`celery_worker.py`) при выполнении задачи делает HTTP POST на сам FastAPI-сервер с `INTERNAL_SERVICE_TOKEN`. Middleware видит service token, проверяет `X-Tenant-Id` и запускает кампанию для указанного тенанта.

## Часть 10: Деплой и инфраструктура

### Docker Compose

Четыре контейнера:
- `app` — FastAPI-приложение
- `postgres` — PostgreSQL
- `redis` — Redis для rate-limit
- `caddy` — обратный прокси с HTTPS

Всё на внутренней Docker-сети. Наружу торчит только Caddy (80 и 443 порты).

### Caddy и HTTPS

Caddy автоматически получает сертификат от Let's Encrypt по доменному имени. Весь HTTP-трафик редиректится на HTTPS. Запросы проксируются на `app:8765`.

### CI/CD

GitHub Actions:
- При пуше в `main` → SSH на VPS → `git pull` → `docker compose up -d --build`
- Перед деплоем запускается проверка конфигурации: `docker compose config`

### .env файл

Все секреты хранятся в `.env` (не в коде):
```env
JWT_SECRET=длинная-случайная-строка-32+
DATABASE_URL=postgresql://user:pass@postgres:5432/maxsender
REDIS_URL=redis://redis:6379
MAX_SERVER_MODE=1
INTERNAL_SERVICE_TOKEN=случайный-токен-для-celery
```

## Часть 11: Что происходит при старте сервиса

1. FastAPI инициализируется, монтирует статические файлы (`/static`)
2. Подключается к PostgreSQL, запускает `init_schema()` — создаёт таблицы если нет, применяет миграции
3. Создаёт admin-пользователя если нет (`ADMIN_EMAIL`, `ADMIN_PASSWORD` из env)
4. Монтирует все роутеры (`routes_auth`, `routes_admin`, `routes_campaign`, и т.д.)
5. Запускает фоновые задачи:
   - `subscription_lifecycle_loop` — мониторинг подписок каждый час
   - `ops_monitor_loop` — мониторинг воркеров и инфраструктуры
   - `backup_loop` — бэкапы по расписанию
6. Если `USE_CELERY=0` — запускает встроенный планировщик для отложенных кампаний

### При остановке (SIGTERM)

1. Устанавливается флаг `shutting_down`
2. Все активные воркеры получают сигнал остановки
3. Текущие сессии MAX шифруются
4. Graceful shutdown — дождаться завершения текущих запросов (до 30 секунд)
